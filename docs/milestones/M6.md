# M6 — Encrypted personal dictionary

Written **before** any M6 work began.

## Scope

1. `PersonalDictionary` in `:core` — an ordered set of **single words**, nothing else.
2. `EncryptedStore` in `:core` — AES-GCM sealing, taking a `SecretKey` from the caller so the
   whole thing is testable on a plain JVM.
3. `KeystoreKeyProvider` in `:app` — the Android Keystore binding, which is the one piece that
   genuinely needs a device.
4. Management UI: list, delete one, delete everything.
5. Full wipe: the file **and** the Keystore key.

## The constraint that shapes the data model

> Never store sentences or keystroke logs.

This is enforced by the type, not by discipline. `PersonalDictionary.add` accepts a single
Hebrew word and rejects anything containing whitespace, punctuation or a second token. There is
no API that accepts a sentence, so there is no code path that could persist one, and no
reviewer has to remember the rule.

Entries are **user-initiated only**. Nothing is added by typing. `SessionStart.mayLearn` gates
writes, so password, email, URI, phone, numeric, OTP-shaped, person-name and postal-address
fields can never contribute — the last two suggest normally but never learn (M4).

## Why the crypto is split across two modules

`:core` holds the sealing and opening and takes the key as a parameter. That makes every
property that can be tested without hardware — round-trip, tamper detection, IV uniqueness,
wrong-key rejection — testable on the JVM in CI. `:app` holds only the Keystore lookup, which
cannot be tested here at all and is recorded as NOT RUN.

## Gates closed in M6, and the positive control for each

| Gate | Asserts | Positive control | Expected |
|---|---|---|---|
| GATE-CRYPTO-1 | No ECB mode, no hardcoded IV/key, no weak cipher or hash, no `SecureRandom` seeded from a constant | `tools/positive_controls/crypto/` — planted `AES/ECB`, a fixed IV, a hardcoded key and `MD5` | gate red on each |
| GATE-DICT-1 | The dictionary cannot hold anything but single words | unit test: every rejection case, plus a would-be sentence | test fails if any is accepted |
| GATE-CRYPTO-2 | Ciphertext is tamper-evident | unit test: flip one byte of every offset class (IV, body, tag) and require a failure each time | test fails if any tamper is accepted |

## Tests planned

- Round-trip over a dictionary with Hebrew content.
- **IV uniqueness across many writes of identical plaintext** — a repeated IV under GCM is
  catastrophic, not merely untidy, so this gets a real denominator rather than a spot check.
- Identical plaintext must produce different ciphertext on every write.
- Tampering with the IV, the body and the tag must each fail.
- Decryption with the wrong key must fail.
- Truncated input must fail cleanly rather than returning partial data.
- Every rejection case for `add`.

## Completion checks

- `./gradlew :core:test` green with the count stated.
- All gates pass with controls shown red.

## What M6 explicitly does NOT cover

- **The Android Keystore binding is NOT RUN.** Hardware-backed key generation, `setUserAuthenticationRequired`,
  StrongBox availability and key invalidation on biometric change all need a device. What is
  tested here is that the sealing is correct *given* a key.
- No key rotation. A single key per install, destroyed on wipe.
- Wiping deletes the file and the key; it does not overwrite the underlying flash, which is not
  something an app can do on Android. Stated rather than implied.
- No backup or export. `allowBackup=false` and the data-extraction rules already exclude
  everything, so the dictionary never leaves the device by that route either.
