# M7 — Accessibility, RTL, robustness, and the latency harness

Written **before** any M7 work began.

## Why the latency harness is the point of this milestone

The build spec is explicit that the sub-50 ms target is **not measurable the obvious way**:

- There is no official IME latency guidance to measure against.
- Macrobenchmark's `StartupTimingMetric` and `FrameTimingMetric` are bound to
  `targetPackageName` and **will never see the IME process**.
- The only working route is `TraceSectionMetric(sectionName = …, targetPackageOnly = false)`,
  an `@ExperimentalMetricApi`, against this app's own `androidx.tracing` sections, driven
  through a trivial host app with an `EditText` via UiAutomator.

> Build that harness or the target is unfalsifiable and therefore not a gate.

So the harness gets built. **It cannot be run here** — there is no device or emulator in this
environment — and that is recorded as NOT RUN rather than papered over with a JVM number
wearing a device's clothes. What this milestone delivers is a harness that assembles, is
committed, and can be run by anyone with a phone.

The trace sections already exist: `CorrectionController` wraps loading in
`HebrewIme.loadLexicon` and each suggestion in `HebrewIme.suggest` (M5).

## Scope

1. `KeyboardAccessibilityHelper` — an `ExploreByTouchHelper` exposing one virtual view node per
   key, so TalkBack can find canvas-drawn keys that are otherwise completely invisible to it.
2. Hebrew letter names in content descriptions. "Shin" is useful; the bare glyph read by a
   screen reader is not.
3. `TYPE_VIEW_HOVER_ENTER` and announcements on layout change.
4. RTL correctness beyond geometry.
5. `:hostapp` — a trivial app with an `EditText`, the target the benchmark drives.
6. `:benchmark` — a `com.android.test` module running `TraceSectionMetric` with
   `targetPackageOnly = false`.

## Gates closed in M7, and the positive control for each

| Gate | Asserts | Positive control | Expected |
|---|---|---|---|
| GATE-A11Y-1 | Every key exposes a non-empty content description, and no two adjacent keys share one | unit test over all three layouts; a fixture layout with a blank description | test fails |
| GATE-TRACE-1 | The trace section names the benchmark asserts on are the ones the app actually emits | a test comparing the constants in `CorrectionController` with those in the benchmark | fails if either is renamed |

`GATE-TRACE-1` exists because the harness is otherwise a silent no-op: `TraceSectionMetric`
looking for a section name nothing emits reports **zero measurements**, not an error. A latency
"result" of no data is exactly the kind of green that means nothing.

## What M7 will NOT cover, stated plainly

- **No latency number is produced.** The harness is built and committed; running it needs a
  device. `docs/QA_MATRIX.md` records p95 keystroke latency as NOT RUN, with the device and API
  level it would need named.
- **No TalkBack verification.** Virtual view nodes are constructed and unit-tested for
  structure, but no screen reader has ever read them. Whether the experience is actually usable
  is unknown and is recorded as such.
- No braille, no switch access, no voice access testing.
- Contrast ratios of the key colours are computed, but perceptual legibility on a real panel
  is not assessed.
