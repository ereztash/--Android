# M8 — Release candidate

Written **before** any M8 work began.

## The blocker, stated first

**Signing requires secrets this environment does not have and must not invent.** The build
rules say to stop and ask the operator when release signing secrets are needed, so M8 delivers
everything up to the signature and stops there:

- the release build configured, minified, and **verified to assemble**;
- a signing config that reads an untracked `keystore.properties` and falls back to an unsigned
  build when it is absent, so the pipeline is complete and testable without the secret;
- the store listing and Data Safety answers written out;
- `docs/QA_MATRIX.md` finalised with PASSED / FAILED / NOT RUN.

**No signed artifact will be produced, and the app will not be described as release-ready.**

## Scope

1. `proguard-rules.pro` and a release build that survives R8. This is a real risk: R8 strips
   what it cannot see reached, and an `InputMethodService` is instantiated by the *system*, by
   name from the manifest, so nothing in the app references it.
2. Verify `assembleRelease` and `bundleRelease` both work.
3. **Re-baseline the DEX for the release variant.** The M2 baseline was taken on a debug build;
   minification changes the descriptor set, and the release artifact is the one that ships.
4. `docs/DATA_SAFETY.md` — the Play Data Safety answers, with the reasoning for each.
5. `docs/STORE_LISTING.md`.
6. `docs/RELEASE_READINESS.md` — the honest verdict.

## Gates closed in M8, and the positive control for each

| Gate | Asserts | Positive control | Expected |
|---|---|---|---|
| GATE-NET-3 | The **release** artifact has no network capability | the same `netcontrol` APK the debug gate uses | gate red |
| GATE-R8-1 | R8 has not stripped the IME service, the settings activities, or anything the system instantiates by name | run the APK gate against the minified release build; a missing service fails `GATE-MANIFEST-1`'s checks | gate red |

## What Play's policy actually requires, and why it matters here

Play has **no IME-specific policy**: there are zero mentions of keyboard, IME or keystrokes in
User Data, Data safety, or the sensitive-API list. What governs is this, and it is decisive:

> User data accessed by your app that is only processed locally on the user's device and not
> sent off device does not need to be disclosed.

So a genuinely offline IME may declare **zero collection** — and that becomes false the instant
any SDK with telemetry enters the build. The Data Safety declaration is therefore not a form to
fill in once; it is a claim that GATE-NET-1, GATE-NET-2 and GATE-NET-3 exist to keep true.

## What M8 explicitly does NOT cover

- **No signed artifact.** Blocked on the operator.
- **No upload to Play.** No account exists, and NOTICE 1's deadline is the operator's to act on.
- **No internal testing track**, which needs the upload above.
- Everything already recorded as NOT RUN stays NOT RUN. M8 does not close device-dependent
  rows by asserting them.
