# M5 — Correction engine and candidate strip

Written **before** any M5 work began.

## The rule that shapes this milestone

> Do NOT set the correction weights or thresholds before a golden corpus exists. Build the
> corpus, hash-lock it, measure a baseline, then choose.

So the order is fixed and is not negotiable:

1. Build the golden corpus and hash-lock it.
2. Implement candidate generation with **neutral, unit weights** — every edit costs 1.
3. Measure the baseline. Record it.
4. Only then choose weights, and justify each one against the baseline.
5. Re-measure and report **both** numbers, before and after, with the corpus hash beside each.

If a weight change improves one metric and worsens another, both get reported. If I ever want
to move a threshold to make a suite go green, that is a STOP-and-report, not an edit.

## How the golden corpus avoids being circular

The engine's headline feature is a **keyboard-adjacency discount**: a substitution by a
physically adjacent key costs less than an arbitrary one. If the corpus's typos were generated
by an adjacency model, measuring on it would be measuring the model against itself.

So there are **three** corpora, hash-locked separately, and they measure different things:

| Corpus | How built | What it measures |
|---|---|---|
| **A — uniform** | Real Hebrew words from held-out Wikipedia, corrupted by one edit chosen uniformly (insert / delete / substitute / transpose), with substitute characters drawn uniformly from the 27 Hebrew letters | The unbiased accuracy number. Adjacency gets no help here. |
| **B — adjacency** | Same words, corrupted by substituting a physically adjacent key | The adjacency feature's own assumption. Reported separately and never merged with A, because it is partly circular by construction. |
| **C — control** | Already-correct words, **unmodified** | The false-auto-replace rate. If this is not near zero, the accuracy numbers from A and B are an artifact. |

A generated typo that is **itself a real lexicon word** is discarded and regenerated, and the
discard count is reported. Correcting such a form is not clearly right, and leaving it in
would depress the numbers for a reason that has nothing to do with the engine — the same bias
§2.3 warns about.

## Scope

1. `HebrewFrequency` — a byte-per-word log-scaled frequency table aligned to the lexicon's
   sorted order, built from source B's counts. 355,587 bytes. Ranking needs frequency and the
   current artifact has none.
2. `Trie` — a flat, array-backed trie over the lexicon, with bounded-edit-distance DFS.
   Node and edge counts to be **measured**, not estimated.
3. `DamerauLevenshtein` — weighted, with transposition.
4. `KeyboardAdjacency` — derived from the actual `Layouts.hebrew` geometry, not hand-listed.
5. `CandidateGenerator` + `Ranker`.
6. Candidate strip UI, and reversible replacement inside a batch edit.

## Gates closed in M5, and the positive control for each

| Gate | Asserts | Positive control | Expected |
|---|---|---|---|
| GATE-ACC-1 | Accuracy is measured against a hash-locked corpus, and the control column's false-replace rate is near zero | corpus C run through an engine variant that replaces indiscriminately | control column shows a high replace rate ⇒ gate red |
| GATE-CORPUS-1 | The corpora are byte-identical across regenerations | fixed seed; a `--inject-defect` reseed changes the hash | gate red |

## Completion checks

- Baseline reported with denominators and all three corpus hashes.
- Weights chosen **after** the baseline, each justified, and before/after both reported.
- top-1, top-3, false_auto_replace_rate and p95 reported, each with the corpus hash.
- Corpus C's correction rate near zero, stated numerically.

## What M5 will NOT cover

- **p95 latency here is a JVM number on this build host, not a device number.** It is a claim
  about `x86_64, 4 vCPU, OpenJDK 17` and is written that way. Real input latency needs the
  `TraceSectionMetric` harness and a device, which is M7, and is **NOT RUN**.
- No language model, no n-gram context, no personalisation. Ranking uses edit cost, unigram
  frequency and prefix analysis only.
- The corpora are derived from Wikipedia prose, so they are not representative of the register
  people actually type in. Stated, not sampled away.
- Corpus B is partly circular by construction and is never merged into the headline number.
