# M4 — SensitiveFieldPolicy and the EditorInfo initial-text discard

Written **before** any M4 work began.

## Why this milestone is the most important one in the project

`TextView.onCreateInputConnection()` calls `outAttrs.setInitialSurroundingText(mText)`
**unconditionally** — including for password fields, with no `inputType` check. An IME is
therefore handed up to 2048 characters of password plaintext in `EditorInfo` without asking
for it and without any way to refuse delivery.

The platform does not solve this. There is no `isPassword()` helper in the public API; the
mask logic has to be written by hand. Everything else in this project is a keyboard feature.
This is the part that decides whether the privacy claim is true.

## Scope

1. `SensitiveFieldPolicy` in `:core` — pure integer mask logic over the restricted field set,
   fully unit-tested with no Android dependency.
2. A session-start API that makes the discard **structural rather than remembered**: the
   initial text is supplied as a lazy provider that is *never invoked* when the field is
   restricted, so the plaintext is never pulled into this process at all.
3. Proactively clearing the `EditorInfo`'s own retained copy on the Android side.
4. OTP detection — best-effort heuristics, failing **closed** to Restricted.
5. Restricted-mode behaviour: no surrounding-text read, no composing text, no suggestions,
   no autocorrect, no learning, no persistence.
6. Session cancellation on field change.

## The restricted field set (§3), as masks

Masked with `TYPE_MASK_CLASS` (0x0f) and `TYPE_MASK_VARIATION` (0xff0). All constants were
verified against `android.jar` API 36 — see `docs/VERIFICATION.md`, 13 of 13 confirmed.

| Field | Value |
|---|---|
| password | 0x81 |
| visible password | 0x91 |
| web password | 0xe1 |
| numeric password | 0x12 |
| email | 0x21 |
| web email | 0xd1 |
| URI | 0x11 |
| phone (class) | 0x3 |
| number (class) | 0x2 |
| `TYPE_TEXT_FLAG_NO_SUGGESTIONS` | 0x00080000 |
| `IME_FLAG_NO_PERSONALIZED_LEARNING` | 0x01000000 |

## Why OTP detection fails closed

An IME **cannot** see autofill hints. `EditorInfo` has no autofill-hints field, and
`TextView.onCreateInputConnection` never writes them into `outAttrs` or its extras.
`androidx.autofill.HintConstants.AUTOFILL_HINT_SMS_OTP` exists but is for autofill services
only. The only signals available are heuristic: `hintText`, numeric + `NO_SUGGESTIONS`, short
`maxLength` shapes, `packageName`.

So OTP detection is **best-effort and fails closed to Restricted**: an ambiguous field is
treated as sensitive. The cost of a false positive is a missing suggestion. The cost of a
false negative is a one-time passcode in a suggestion database.

## Gates closed in M4, and the positive control for each

| Gate | Asserts | Positive control | Expected |
|---|---|---|---|
| GATE-PRIV-1 | Initial text is never read for a restricted field — **tested with a field that DID contain text**, otherwise the test is blind | `tools/positive_controls/privacy/` — a service file calling `getInitialTextBeforeCursor` outside the policy boundary | gate red |
| GATE-PRIV-2 | The `Initial*` accessors are referenced **only** inside the policy boundary file | same fixture | gate red |
| GATE-PRIV-3 | A restricted session yields no composing text, no suggestions, no learning, no persistence | unit test: a policy variant that leaks | test fails |

The provider design is what makes GATE-PRIV-1 testable rather than aspirational: the test
supplies a provider that returns a real password string and records whether it was called.
Asserting "the returned text is null" alone would pass even if the text had been read, copied
and logged first. Asserting **"the provider was never invoked"** is the claim that matters.

## Tests planned

- Every one of the 11 restricted values classifies as Restricted, and a plain text field does
  not. Denominator stated.
- Exhaustive sweep: **all 4096 variation values** against `TYPE_CLASS_TEXT`, asserting no
  value outside the known-safe set is silently treated as Normal.
- A field that contains a real password string: provider never invoked, text never retained.
- `IME_FLAG_NO_PERSONALIZED_LEARNING` alone forces Restricted even for plain text.
- Unknown/future input-type classes fail closed.
- OTP heuristics, each signal separately and in combination.

## What M4 explicitly does NOT cover

- **No device testing.** That the framework really does hand over password plaintext is taken
  as true and defended against unconditionally; it cannot be confirmed from `android.jar`,
  whose method bodies are stubs. The defence is correct whether or not the framework populates
  the field, which is the safe direction to be wrong in.
- Restricted mode is enforced at the policy boundary. It does **not** prove that no other code
  path anywhere logs text; that is a whole-program property this gate does not establish.
- OTP detection is heuristic and its accuracy is **NOT MEASURED** — there is no labelled corpus
  of OTP fields to measure against, and one is not fabricated here.
- No persistence exists yet, so "no persistence in restricted mode" is currently trivially
  true. It becomes a real constraint at M6.
