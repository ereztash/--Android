# M10 — predictive input

**Requirement, from the operator:** *"האפליקציה צריכה להיות פרדיקטיבית, לחזות את מה שהמשתמש
רוצה לכתוב ולהציע לו, ואם יש שגיאת כתיב לשים לב אליה"* — the app must be predictive, foresee
what the user wants to write and offer it, and notice spelling errors.

## Plan (written before the work, per §0)

| # | Step | Gate |
|---|---|---|
| 1 | Source word-order data. The lexicon was built from a verb list and a **frequency** list; a frequency list records how often a word occurs and nothing about order, so the information prediction needs was never in the sources. | — |
| 2 | Build a bigram model from Hebrew Wikipedia, splitting on sentence boundaries before counting. | GATE-BIGRAM-1 |
| 3 | Build an evaluation corpus **proven** disjoint from the training data. | build script refuses to write on any overlap |
| 4 | Measure a baseline **before** choosing any weight. | — |
| 5 | Sweep, choose, record the whole table including the worse rows. | — |
| 6 | Wire it into the IME behind the existing restricted-field policy. | GATE-API-1 unchanged |
| 7 | Lock the numbers with floors set from the baseline, plus controls. | `PredictionAccuracyTest` |
| 8 | Pay for the size honestly. | GATE-SIZE-1 |

## What shipped

- `BigramModel` — 54,133 groups, 532,168 pairs, 2.95 MiB of heap, one binary search plus a
  contiguous read per lookup.
- `PredictiveEngine` — completion, correction and next-word over one lexicon, with the three
  kinds kept separate rather than blended into one opaque ranking.
- `InputContextBuffer.previousWord` — null after a desync, null in a field whose initial text
  was withheld, and null across a sentence boundary.
- `CandidateStripView` now renders `Prediction`, marks corrections distinctly, and — new in
  M10 — exposes each candidate as a virtual view node. Before this the whole strip was one
  blank rectangle to TalkBack and no suggestion was reachable at all.
- `GATE-BIGRAM-1`, `GATE-SIZE-1`, and four locked accuracy assertions with three controls.

All measurements: [`docs/PREDICTION_MEASUREMENTS.md`](../PREDICTION_MEASUREMENTS.md).

## Three defects this milestone found, none of them in the new code

### 1. The ordering of corrections and completions had never been measured

The engine put corrections first whenever the typed string was not a lexicon word, on the
reasoning that the word is wrong as it stands. Measured against both corpora at once, that
policy was **dominated** — worse on completions *and* worse on typos, every column. It was not
a defensible position that lost narrowly; it was a guess that had never been checked. Shipped
value moved to `COMPLETIONS_FIRST`, and the prefix-3 accuracy floor was **raised** from 42.0 to
48.0 to lock the gain in.

### 2. `isCombiningMark` classified four punctuation characters as marks

`U+0591..U+05C7` holds te'amim and niqqud — and maqaf, paseq, sof pasuq and nun hafukha, which
are `Pd`/`Po`, not marks. The predicate was written for `stripPoints`, where over-inclusion is
harmless. When `InputContextBuffer` later borrowed it to decide *what counts as part of a
word*, the over-inclusion became a bug: `שלום׃ מה` was one word ending in a full stop, so
neither half got suggestions and a bigram query crossed a boundary the model was never trained
on.

Found by a new test that checks all 55 code points in the range against `Character.getType` —
the JDK's own Unicode tables — rather than against a list written in the test. A hand-written
expectation would have agreed with a hand-written implementation and proved nothing, which is
exactly how the mirrored keyboard survived M3 through M8. `stripPoints` behaviour was
deliberately left unchanged: every lexicon lookup depends on that reduction, and narrowing it
is a separate question needing its own measurement.

### 3. A missing asset would have killed the keyboard, not degraded it

`AssetManager.open` throws when an asset is absent, and an uncaught throw inside `scope.launch`
reaches the thread's default handler and takes the IME process with it. A keyboard that will
not start is a phone the user cannot type on — far worse than a keyboard with no suggestions.
Each stage now degrades instead, and the guarantee lives on the artifact: `apk_lexicon` and
`apk_bigrams` fail the build when an asset the code opens by name is missing or does not hash
to its manifest.

That gate immediately caught a real instance: the release APK still on disk had been built
before the bigram table existed and shipped without it. `GATE-BIGRAM-1` went red on the first
run against it.

## What M10 does NOT do

- **No trigram or longer context.** Two words is the entire memory. There is no notion of a
  sentence, a topic, or the user's own vocabulary.
- **No learning from what the user types.** The personal dictionary from M6 is still
  user-initiated entries only, and prediction does not read it. Wiring it in is a real
  improvement and a real privacy question, and it is not smuggled in under "predictive".
- **No real-word error detection.** `אם` where `עם` was meant is untouched here: both are
  perfectly good words, so nothing in this milestone can see the problem. That is M11.
- **No device latency number.** `HebrewIme.suggest` now covers more work than it did in M7, so
  the M7 baseline does not describe this code. Re-measured in M12.
